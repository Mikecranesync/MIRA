# `wiki/hot.d/` — one file per automated run

Machine-written run notes. **One run writes exactly one new file**; nothing here is
ever appended to by a second writer.

```
wiki/hot.d/YYYY-MM-DD-<writer>-<worker>.md
```

Today: `<writer>` is `eval-fixer` (the nightly agent, `.claude/agents/eval-fixer-instructions.md`
Step 10), and `<worker>` is the slugified short hostname of the node that ran it
(override: `MIRA_EVAL_FIXER_WORKER`). Any future automated writer that produces a per-run
note takes a new `<writer>` name and the same date+worker-per-file shape.

**The `<worker>` segment is not decoration.** The date alone is not a unique key: this repo is
kept identical across CHARLIE / ALPHA / BRAVO by Ansible, so the same nightly job can fire on
more than one node on the same date. Two same-date workers sharing a filename reintroduces the
exact collision this directory exists to remove — measured, not assumed (see § **Evidence**).
Because the worker id is *stable per node*, a restarted run resolves the same filename and
overwrites in place, so an interruption still produces one file rather than two.

**Naming does NOT solve same-host concurrency — a lock does.** A scheduled run and a manual
re-run on one machine resolve the same hostname, therefore the same worker, therefore the same
path. No filename scheme fixes that, because by every stable identity they have they *are* the
same worker. So the path is not generated by hand:

```bash
python3 tools/eval_fixer_fragment.py --date "$(date +%Y-%m-%d)" --acquire   # prints the path
python3 tools/eval_fixer_fragment.py --date "$(date +%Y-%m-%d)" --release
```

`--acquire` takes an atomic host+date lock and **rejects a second concurrent run (exit 2)**
rather than letting it race. A lock left by a crashed run is reclaimed after 6h, so a retry is
never blocked forever. An override that normalizes to nothing (`MIRA_EVAL_FIXER_WORKER='!!!'`)
**exits 3** instead of silently producing `…-eval-fixer-.md`. To run a second worker on one
host deliberately, give it a distinct `MIRA_EVAL_FIXER_WORKER`.

## Why this exists

`wiki/hot.md` is a **shared line**. Every eval-fixer run used to append to its tail, so
each night's PR edited the same lines as every other pending night. Those PRs went
CONFLICTING — and **a conflicting PR receives no CI at all**, because GitHub cannot build
the merge ref. The run notes stopped being verified while still looking open and healthy.

Four runs piled up that way before this was fixed (#2994, #3036, #3050, #3087). Two of them
still read MERGEABLE against `main` while **mutually** conflicting: merging either one
instantly broke the other.

Putting each run at its own path removes the collision at the source. Two runs on different
dates touch different files, so they always merge cleanly — no merge driver, no
`.gitattributes`, no generated index.

`merge=union` was considered and rejected: `wiki/hot.md` is **not** strictly append-only
(measured over its last 40 commits: +1140 / −9 lines, with deletions in 4 of them), so union
would silently duplicate content on the commits that edit rather than append.

## Finding things

These are dated files — read them newest-first:

```bash
ls -r wiki/hot.d/                            # newest run first
ls wiki/hot.d/"$(date +%Y-%m-%d)"-*.md       # today's runs (all workers)
grep -rl "issue-filed" wiki/hot.d/           # every run that filed instead of patching
```

**There is deliberately no generated index file here.** A committed
`hot.d/INDEX.md` regenerated by each run would be a shared line again, under a new
filename — the exact problem this directory exists to remove.

## Evidence

A synthetic concurrency harness ran the worker exactly as Step 10 specifies, across throwaway
git repos: different dates, concurrent same-date workers, interrupted+restarted runs, unrelated
files under `wiki/` and `wiki/hot.d/`, and midnight boundaries. On the date-only filename it
scored **41 passed / 2 failed**, and both failures were the same-date case:

```
[FAIL] same-day workers write DIFFERENT files
       ['wiki/hot.d/2026-08-04-eval-fixer.md', 'wiki/hot.d/2026-08-04-eval-fixer.md']
[FAIL] concurrent same-date runs merge conflict-free
```

With the `<worker>` segment, both pass and every merge order is conflict-free. That is why the
segment exists.

Every one of those scenarios is now a committed test that runs in CI — the scratch harness is
superseded, so the evidence is re-runnable rather than a number in a PR body:

| Scenario | Test |
|---|---|
| Different dates, all merge orders | `test_two_dated_runs_merge_cleanly` |
| Same-date workers (naming) | `test_same_date_workers_do_not_collide` + its control |
| **Same-host concurrency (lock)** | `test_same_host_same_date_concurrent_second_run_is_rejected` |
| Interrupt → restart | `test_retry_after_release_reuses_the_same_path` |
| Crashed run does not block a retry | `test_stale_lock_from_a_dead_run_is_reclaimed` |
| Foreign WIP in a dirty shared tree | `test_run_does_not_sweep_foreign_wip` |
| Midnight boundary | `test_midnight_boundary_runs_do_not_collide` |
| Worker-id normalization + fail-closed | `tests/test_eval_fixer_fragment_helper.py` |

## Rules for writers

1. **One run → one new file**, named for its date **and worker**. Never append to another run's file.
2. **Never modify `wiki/hot.md`.** That file is human session notes.
3. **Stage the fragment by its exact path** — never `git add wiki/`, `-A`, or `.`; the
   working tree is shared and may hold another session's work.
4. **Re-running on the same date overwrites that date's file in place.** No suffixes,
   no counters, no second file.

Enforced by `tests/test_eval_fixer_fragments.py`.
