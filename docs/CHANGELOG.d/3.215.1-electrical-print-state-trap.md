# v3.215.1 — Release stale ELECTRICAL_PRINT state on a new diagnostic intent

Date: 2026-07-26

**Prod/staging bot outage fix.** A chat left in `ELECTRICAL_PRINT` state (from a prior
schematic-photo turn) trapped **every** subsequent text message: the dispatch guard in
`Supervisor.process()` fired on `state == "ELECTRICAL_PRINT"` alone, with no check on the new
turn's router intent, so even a clean `diagnose_equipment` query was force-routed into
`_handle_electrical_print_followup`.

Same root cause took the two surfaces down differently:

- **prod** — the print/vision follow-up path uses Together `MiniMaxAI/MiniMax-M3` (~77s), which
  blows past the bot's 30s `PROCESS_TIMEOUT` → silent bot.
- **staging** — the print worker endpoint is `disabled://` → httpx unsupported-protocol →
  `PRINT_WORKER_ERROR` → generic-error + KB-gap fallback.

**Fix:** when the router reports the user has moved on to diagnosing specific equipment
(`diagnose_equipment`) or is starting over (`greeting_or_chitchat`), release the print state to
`IDLE` and fall through to normal routing (new `_PRINT_STATE_EXIT_INTENTS`). Genuine print
follow-ups classify as `answer_question` / `continue_current` and still stay in the print handler,
preserving #2817/#2820. Per-session unblock remains `/new`.

Regression coverage: `mira-bots/tests/test_engine_print_state_exit.py` (red on the unconditional
guard, green after). Incident 2026-07-26.
