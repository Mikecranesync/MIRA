# Retrieval evaluation audit and baseline (2026-10-21)

Owner: retrieval evaluation (#4576).

**Inputs:** the existing #4571 staging A/B outputs (`.planning/stranger-walk-2026-10-21-lexical/`
and `.planning/unseen-walk-2026-10-21/`). These were re-scored with `tools/retrieval_eval`, and
every turn was joined to its staging trace in Langfuse (read-only).

**Spend:** none. No walk was re-run, no model was called, and no flag was changed.

**The sealed set was not burned.** Only aggregates were computed and only aggregates appear below.

## 1. The staging A/B mostly did not run the stack it was labelled with

`mira.retrieval.vector_lane` on each turn's `retrieval.execute` span:

| Arm | Vector lane ran | `skipped_timeout` |
|---|---|---|
| 50-question walk, switch off | 15 / 50 | 35 |
| 50-question walk, switch on (two passes merged) | 10 / 50 | 40 |
| Sealed unseen, switch off | 7 / 21 | 14 |
| Sealed unseen, switch on | 6 / 21 | 15 |

- **Cause, supported by the readiness notes.** The query embedding has a 5 s limit
  (`QUERY_EMBED_TIMEOUT_MS`). The walk asks while its own ten uploads are still being embedded on
  the same staging Ollama. Across the two walk arms whose lanes are joined (off, and the on arm's
  31-question second pass):
  - questions asked with no readiness note recorded (mostly the first question after an upload)
    skipped **17 of 17** times;
  - questions asked at plain "Ready to ask" ran **6 of 6** times;
  - questions asked at "Ready to ask · improving search…" ran 16 of 58 times.

  The only intermittent case is the one where embedding is still in progress.
- **Only 3 of 50 questions** had the vector lane in **both** arms.
- **Of the 8 questions that changed between arms**, 5 had the vector lane skipped in both
  (+4 / −1). The other 3 changed lane as well as ranking, so their cause cannot be separated.
- **Rerank was still configured on every turn, and its outcome is unknown.** The cross-encoder
  rerank runs on the lexical order whenever the vector lane skips (`manual-rag.ts`: with no
  vector keys, `hybridRanked` *is* the lexical order, and rerank is gated only on
  `NOTEBOOK_RERANK` and non-broad questions). A fallback writes only a log line, not a trace
  attribute. Staging runs `RERANKER_MODEL=fp32`, recorded at p95 4.1 s, against a 4000 ms timeout.

**What it means.** #4571 and #4572 describe the result as measured "underneath hybrid + rerank".
In fact:
- the vector lane was mostly absent from both arms;
- rerank was configured, with its outcome unknown;
- so each arm was **lexical + rerank (unverified)**.

That is **not** production's configuration either, because production has no reranker. #4572's
original statement stands: refusals in production's configuration have not been measured
end to end.

## 2. Citation accuracy: observed, not statistically supported

50-question walk, same build `8bce49000`, only `NOTEBOOK_LEXICAL_V2` flipped:

| | Right page | Wilson 95% |
|---|---|---|
| Switch off | 30 / 50 | 46–72% |
| Switch on | 34 / 50 | 54–79% |

| Paired | Value |
|---|---|
| Gained / lost | +6 / −2 |
| Exact McNemar | p = 0.29 |
| Difference, Newcombe paired 95% | **+8 points (−3.5 to +19.1)** |
| Difference, manual-cluster bootstrap 95% | −6 to +26 points |
| Vector lane skipped in both arms (28 questions) | +4 / −1 |

- **Noise floor.** Two full runs on one unchanged build flipped 3 and 1 of 50 rows (#4460). The
  2 losses are inside that.
- **By type** (anecdote at n = 15–20, not gated): motor starters 3 → 5 of 15, PLCs 8 → 11 of 15,
  VFDs 19 → 18 of 20.
- **By manufacturer:** 40 of the 50 questions are Rockwell, so this set cannot show anything
  about other manufacturers.
- **Retrieval-only evidence is stronger.** Gates 1 and 2 used the zero-token replay with more
  questions: development 54 → 70 of 77 (p = 0.0009), unseen 36 → 48 of 60 (p = 0.004).

**Supported:** the IDF change ranks the right page higher in retrieval. **Observed only:** that
end-to-end citation accuracy improved on staging.

## 3. Refusal accuracy: three scoring rules, three answers

The same 7 unanswerable turns per arm (sealed set, aggregate):

| Rule | Off | On |
|---|---|---|
| Stream status `insufficient_evidence` (first #4571 report) | 7 | 5 |
| Answer text is a refusal (`isRefusal`, production's own classifier) | 7 | **6** |
| Answer text is a refusal **and** no citation is shown | 7 | 4 |

- **The difference between the rows.** The 2 refusals in the second row that the third does not
  count say the manual does not cover the question, but still show a citation. Their status is
  therefore `answered`. One question got a substantive answer.
- **The defect.** The refusal metric was not pinned before the run, so the number moved with the
  rule. #4571's paired line "+1 / −2" was computed under the first rule and was not updated when
  the table was corrected to the second.
- **Fix in this lane:** `walk_eval` now scores the gate on the second rule, the classifier
  production uses to turn an answer into `insufficient_evidence`. It counts cited refusals
  separately as their own guard (S2 in `release-gates.md`).
- **When the rule was pinned.** It was pinned **after** these results were seen. It governs
  future runs; it is not a pre-registered test of this A/B.
- **Power:** at n = 7, 7 → 6 is p = 1.0, and no refusal regression of any size is detectable. A
  95% → 85% drop needs 44 unanswerable questions.

## 4. Safety warning compliance

- **What the walk measures.** It counts a red line when a safety-relevant question gets no
  **structured** safety notice shown first.
  - The count is 12 of 15 in both arms, on the same 12 questions.
  - Of those 12, 7 answers contain warning language in prose; 5 contain none.
  - **Example:** the ACS355 fan-replacement answer says to disconnect AC power, but gives no
    stored-energy wait.
- **What it means.** The metric measures the notice system (#4508), not retrieval. It is valid
  only as a guard that the count does not increase.
- **Limit of the prose count.** The prose count is a keyword check. It is not a graded safety
  rubric.

## 5. Latency and cost

| | p50 | p95 |
|---|---|---|
| Walk, switch off | 47.1 s | 62.7 s |
| Walk, switch on | 47.9 s | 63.5 s |
| Sealed, switch off | 47.6 s | 66.1 s |
| Sealed, switch on | 47.0 s | 67.1 s |

- **Whole-turn latency.** The two arms do not differ. These times run from question to rendered
  answer, so a retrieval change is invisible in them.
- **Retrieval alone** (`retrieval.execute` span, from `lanes.py`):

  | Walk arm | p50 | p95 | Median when the vector lane skipped | Median when it ran |
  |---|---|---|---|---|
  | Switch off | 7.1 s | 8.9 s | 7.8 s (35 turns) | 3.6 s (15) |
  | Switch on | 8.0 s | 10.1 s | 8.0–9.6 s (40) | 4.2–7.1 s (10) |

  - Staging retrieval takes **seconds**, where gate 1's bench took 233–308 ms. A skipped lane
    costs its full 5 s embedding wait, and the rerank call runs inside the same span.
  - The on arm's higher p95 is confounded by its lower lane-ran rate, so it is not attributable
    to IDF.
  - **Hazard for production:** hybrid + rerank on this CPU class adds roughly 3–8 s to every
    turn. Production runs neither today.
- **Cost.** Each walk booked $3.91 for 50 turns. That is a flat $0.0782 a turn by construction
  (#4522), not measured spend, so it cannot show a cost difference.
