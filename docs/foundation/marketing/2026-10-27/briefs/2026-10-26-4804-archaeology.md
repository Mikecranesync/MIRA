## 1. Is the claim real?
- `conversation_router.py:93-103` (per issue; consistent with file) embeds raw `user_message` in the user turn. Real.
- `engine.py:3372-3384` `_router_intent = _routing["intent"]`; `engine.py:3670-3679` dispatches `log_work_order`→`_handle_wo_request`, `switch_asset`→`_handle_asset_switch`, `check_equipment_history`→`_handle_check_equipment_history` on `_router_intent` alone. - **But the "privileged action" part is overstated:**
  - `log_work_order` (`_handle_wo_request`, engine.py:6870-6905) only builds a **draft preview** and arms `cmms_pending`. Nothing is written to a CMMS. Actual creation happens only in `_handle_cmms_pending` (engine.py:4702ff) when the user then replies yes (`_CMMS_YES`, :4602) and the draft passes `wo.is_valid` (:4783-4803) → `_post_cmms_work_order` (:4806). So a confirmation step exists. The injector is the same user who would type "yes" — injection gains nothing they couldn't get by saying "create a WO" (there's also a regex fast-path, `_WO_ACTION_REQUEST_RE`, per issue ~:3278).
  - `check_equipment_history` (:7131-7175) reads local SQLite `interactions` **WHERE chat_id = ?** — the caller's own chat only. Not Atlas, not tenant-wide. "Exfiltrate the tenant's WO history" is **not supported** by the code.
  - `switch_asset` (:6767ff) clears the caller's own FSM/session context. Self-only state reset.
- Net: a misroute/injection risk (UX + spurious drafts), not a privilege escalation. Issue's 🔴 should be 🟡.
