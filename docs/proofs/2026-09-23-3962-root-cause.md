## The experiment

Same SHA, same photo, same three-step sequence from the issue, six runs. The only

| **with** `history` | **the bearing** — lubrication, wear, misalignment | **3 / 3** |

## The earliest point where correct evidence stops influencing the answer

The packet for a failing run:

```json
"visual_evidence": { "observation_in_context": true, "prior_turn_observation_count": 1 }
"generation":      { "has_observation_text": true }
"context":         { "visual_evidence_count": 1, "system_prompt_kind": "general",
                     "history_turns": 0, "prompt_chars": 3439 }
```

The observation **did** reach the model. So the failure is not "evidence was
dropped" — the recall feature (#3943/#3944) works exactly as designed.

**What reaches the model is a description of a LABEL, not an identification of a
machine.** Measured across four identical LOOK calls, the observation reads:

> "A white rectangular product label is affixed to a brown cardboard surface. The
> label contains a barcode and printed text. Readable text: `32906X Tapered Roller
> Bea...`, `Width 2pcs`, `MADE IN CHINA`…"

It contains the word *bearing* in **0 of 4** runs — the label is physically
truncated — and describes cardboard and a barcode. Asked "it is chattering, what
do I check first", a model holding *that* plus no other context has nothing
connecting the label to the symptom, and falls back to its strongest prior for
"chattering": contactor/drive chatter.

**The identification lived in turn 1's ANSWER** — "it's a tapered-roller bearing".
That is the piece of correct information that exists and then stops influencing
the answer, and `history_turns: 0` is where it is lost.

## The server-side gap this exposes (fact, not inference)

`history` is **entirely client-supplied**: the route does
`const history = sanitizeHistory(body.history)` and reconstructs nothing. Meanwhile
the server *does* recall the prior **observation** by itself.

So the recall feature is **half-complete**: it carries the raw perception across
turns but not the interpretation MIRA itself derived from it. Any surface that
loses history — a new device, a cleared session, a thread past the client's cap, a
client bug — gets the label without the meaning, and reproduces #3962 exactly.

## What this means for the issue as filed

- **Confirmed:** the failure is real, reproducible 3/3, and the packet evidence in
  the issue is accurate.
- **Confirmed:** both real clients send history — Hub via `historyFromTurns`
  (`notebook-chat-utils.ts`), mobile via `history: body.history`
  (`NotebookScreen.tsx`). With history the answer is correct 3/3.
- **Inference (not established):** the original observation came from
  `photobench.py`. If that harness did not send history — as my first attempt did
  not — then the filed reproduction exercised a path the real surfaces do not
  normally take. This does **not** make the issue invalid; it relocates it.

## The fix this points at

Not prompt wording. When the server recalls a prior observation, it should also
carry the **subject MIRA already established** for that observation, so the
recalled evidence is self-sufficient rather than dependent on the client
remembering to send history.

The architecture for this already exists and is already on that code path —
`listTurns` is loaded in the same prior-turn fetch that produces `priorLookRows`.
No new system, no new registry, no lexical matching.

**Deliberately not implemented here.** #3964 is the capture slice and is already
blocked; a behavioural change to the answer path belongs in its own PR with its
own regression test — one that reproduces this exact failure (photo → follow-up,
history withheld) and asserts the answer stays on the subject.

## What NOT to do

Do not widen `ANSWER_IGNORED_VISUAL_EVIDENCE`'s keyword vocabulary to catch this.
The detector missed 2 of 3 because the observation never contains the word
*bearing*; padding the vocabulary would fit three samples and rebuild #3963. The
structural replacement — lineage from `observation id → selected for context →
present in model input → referenced in answer` — is the right direction, and it
should stay shadow-only until it is measured.
