## Registry changes made

- **Five new per-component entries** — `apps-plc-reader`, `services-diagnosis`,
  `services-telegram-bot`, `services-llm-router`, `services-plc-modbus`. The parent `apps` /
  `services` entries are directory-granularity and carried one wholesale status; each nominated
  component now carries its own status on its own evidence. Keys are hyphenated, not slashed.
  To be precise about why: Contract 14 itself only validates the `tags:` vocabulary, but the
  scanner it uses counts entries with `_TOP_KEY_RE = ^[A-Za-z0-9_.-]+:`, which does not admit `/`.
  A slashed key would therefore have its `tags:` line counted while the key itself was not counted
  as an entry, so `tag_lines != entries` and the contract's test fails. The constraint is the
  scanner's key regex, not the taxonomy rule.
- **Three downgrades** — `sim`, `cosmos`, `cookoff`: `DELETE_CANDIDATE` → `LEGACY`, each with
  `blocking_evidence`.
- **One confirmation** — `simulation` stays `DELETE_CANDIDATE`, now with `clearing_evidence`.
- **Parent-entry drift recorded** — `services.known_drift` gains F11 (two live services inside a

## Gate 7 — adversarial review

### The real lane could not review this diff — and finding out why was itself a defect

`tools/gate7_review.py 3283` ran at **xhigh** (triggers: security boundaries, cross-repository
contract) and returned **BLOCK** with two high-severity findings: *"duplicate top-level keys
`[SN]` cause data loss"* and *"placeholder `[SN]` used as a key and as a path component"*.

Both are artifacts of the lane's own egress sanitizer, not defects in the change. The lane reuses
the canonical PII regexes from `mira-bots/shared/inference/router.py`, and `_SERIAL_RE` matches the
ordinary word **"service"**:

```python
_SERIAL_RE = re.compile(
    r"\b(?:S/?N|SER(?:IAL)?(?:\s*(?:NO|NUM|NUMBER)?)?)[:\s#]*[A-Z0-9\-]{4,20}\b",
    re.IGNORECASE,
)
```

The `SER` alternative matches the `ser` in `services`; `[A-Z0-9\-]{4,20}` then eats `vices`; and
`[:\s#]*` permits zero separators. Demonstrated:

| Input | After redaction |
|---|---|
| `services-diagnosis:` | `[SN]:` |
| `services-telegram-bot:` | `[SN]:` |
| `path: services/diagnosis/` | `path: [SN]/diagnosis/` |
| `multi-service stack` | `multi-[SN] stack` |

So the reviewer received four entries all keyed `[SN]:` and correctly reported that as duplicate
keys — a sound conclusion from corrupted input. The actual file loads cleanly (`yaml.safe_load`
→ 80 distinct top-level keys) and CI's **Architecture Check passed**, which is Contract 14 run
against these exact entries.

This is not only a review-lane problem. `sanitize_context()` is default-on for every cascade call
(`complete(..., sanitize: bool = True)`), so the same regex mangles **production technician
turns** — "Check the service manual for the PowerFlex 525" reaches the model as "Check the [SN]
manual for the PowerFlex 525". Filed as **#3305** with a reproduction table and a suggested fix.
Not fixed here: changing a default-on security control on the production inference path deserves
its own unit, R0 and gates. It is the second defect this lane has produced (after #3278, diff
truncation).

There is no flag to disable redaction — `redact()` deliberately fails loud, not open. So the real
lane **cannot** faithfully review any diff containing the word "service", which this one does
throughout.
