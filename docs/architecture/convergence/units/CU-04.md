## Runtime-consumer sweep — CHARLIE (first pass)

Evidence gathered on CHARLIE, 2026-08-17. Commands and raw results, not summaries.

### F1 — `CLUSTER.md`'s CHARLIE Telegram-poller claim is **REFUTED**

`CLUSTER.md:170` states, under "CHARLIE — Vector KB + Telegram Ingress":

> **Telegram bot** via polling (`services/troubleshoot/adapters/telegram_bot.py`) — uses
> `run_polling()`, no public endpoint or webhook needed.

Three independent checks say it is not running:

| Check | Result |
|---|---|
| `ps aux \| grep -iE "troubleshoot\|telegram_bot\|adapters/telegram"` | **no matching process** |
| every `~/Library/LaunchAgents/*.plist` grepped for factorylm paths | 5 jobs reference factorylm; **none references `troubleshoot`** |
| `crontab -l` | **no crontab at all on CHARLIE** |

The directory `factorylm/services/troubleshoot/` does exist, so an in-repo grep would have
"confirmed" the claim. That is precisely why §Gate 11 forbids grep as sufficient evidence:
**the code is present and nothing runs it.**

⇒ `CLUSTER.md` is stale on this point. Filing separately rather than fixing here (CU-02's
precedent: record drift, don't silently absorb it).

### F2 — `com.factorylm.health-monitor` is a loaded launchd job that cannot run

```
$ launchctl list | grep health-monitor
-	127	com.factorylm.health-monitor          # exit status 127 = command not found

$ ls -la /Users/charlienode/factorylm/scripts/health-check.sh
ls: scripts/health-check.sh: No such file or directory
```

The job is **loaded and scheduled**, its target script **does not exist**, and it has been
exiting 127 on every invocation. A health monitor that monitors nothing, failing silently.
Unrelated to the nine components but found by this sweep, so it is recorded rather than
dropped.

### F3 — the nine nominated components all exist; none is referenced by CHARLIE's live jobs

All nine are present on disk in `factorylm/`. CHARLIE's five live factorylm-referencing launchd
jobs are `brain-mcp`, `brain-ingest`, `health-monitor` (broken, F2), `jarvis-node`, and
`mira-offline-eval` (which runs out of `MIRA/`, not `factorylm/`). **None** of them invokes
`services/diagnosis`, `services/telegram_bot`, `services/llm-router`, `apps/plc-reader`,
`services/plc-modbus`, `sim`, `simulation`, `cosmos`, or `cookoff`.

**No status is being asserted yet.** "Not referenced by CHARLIE launchd" is necessary but far
from sufficient for `LEGACY` / `DELETE_CANDIDATE` — compose wiring, deployment scripts, BRAVO,
and the PLC laptop are still unchecked.

### Known gap in the evidence: ALPHA is unreachable

`CLUSTER.md` records ALPHA as **retired from the cluster 2026-08-16**, repurposed as a household
PC, no longer the SMB host or orchestrator. Its launchd and crontabs therefore cannot be
inspected. This is stated as a limitation rather than silently treated as "no consumers found" —
a node you cannot inspect is not a node you have cleared.
