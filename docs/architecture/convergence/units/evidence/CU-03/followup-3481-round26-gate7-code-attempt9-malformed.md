## FINDINGS
- **[severity: high] Duplicate logical rows can be created when inserting a canonical URL that already exists in the database under a non‑canonical (historically‑cased) spelling** — the historical‑spelling guard in `store.insert_chunk` only runs when the caller‑supplied URL differs from its canonical form. If the caller supplies the canonical spelling while a legacy row with the same logical document but a different case (e.g. `"HTTPS://EXAMPLE.COM/Doc.PDF"` stored as `"HTTPS://EXAMPLE.COM/Doc.PDF"` or `"https://example.com/Doc.PDF"` stored as `"HTTPS://EXAMPLE.COM/Doc.PDF"` after a rename) already exists, the guard is bypassed, the `ON CONFLICT` clause does **not** fire (the conflict key is `(tenant_id, source_url, chunk_index)`, which does not match the legacy row), and a **second row** is inserted. This violates the dedup guarantee that a logical document must map to a single `knowledge_entries` row, opens the door to data‑corruption, double‑counting in downstream KG linking, and makes the ledger probe (`ingested_source_urls`) report “ingested” for the same logical URL under two different keys.

  **Why the bug is not covered by existing tests**  
  The test suite only checks the guard when the caller passes a *raw* (non‑canonical) URL:

  ```python
  def test_insert_itself_never_writes_beside_a_historical_raw_spelled_row(self, captured):
      captured["count"] = 1  # DB already holds the row under the raw spelling
      raw = "HTTPS://EXAMPLE.COM:443/Legacy%7a.PDF"
      assert _insert(True, raw) == ""
  ```

  It never exercises the complementary path where the DB already holds a raw‑cased row **and the caller supplies the canonical spelling**. In that case `raw_url == source_url` after canonicalisation, the guard is skipped, and the INSERT proceeds, creating a duplicate row. No test asserts that `captured["count"]` = 1 with a raw‑cased row and a canonical insert returns an empty string.

  This is precisely the “case‑insensitivity” defect the brief warned about: the system treats two spellings that differ only in case as distinct keys, even after the canonicalisation fix, because the pre‑insert existence check is conditional on `raw_url != source_url`.

## NOT REVIEWED
- The impact on downstream KG‑linking and `store_chunks` counting has not been exercised in integration tests; a duplicated row will be counted as a new successful chunk and linked to equipment, inflating KG statistics.
- No test verifies that `ingested_source_urls` correctly reports a single logical URL when both a raw‑cased and a canonical row exist after such a duplicate insert; the function will return both spellings, breaking the “one key per logical document” invariant.
- The migration that adds the unique index on `(tenant_id, source_url, ((metadata->>'chunk_index')::int))` already protects against exact‑match duplicates, but it does **not** protect against case‑variant duplicates because the index is case‑sensitive on the `source_url` column. This bug therefore re‑introduces the pre‑fix problem that the migration sought to eliminate. 

## RECOMMENDATION (for the author)
1. **Unconditional pre‑insert existence check** – call `chunk_exists(tenant_id, source_url, chunk_index)` **after** canonicalisation, regardless of whether the original URL differed from its canonical form. If any row (raw or canonical) exists, abort the insert and return `""`.  
   ```python
   raw_url = source_url
   source_url = canonical_source_url(source_url)

   # Always check for any existing row (raw or canonical)
   if chunk_exists(tenant_id, source_url, chunk_index):
       return ""
   ```
   Optionally keep the historical‑spelling shortcut for an early exit when `raw_url != source_url` to avoid an extra query, but also run the check when they are equal.

2. **Update tests** – add a test case that seeds the fake DB with a raw‑cased row (`captured["count"] = 1` with `captured["url"]` set to the raw spelling) and then calls `_insert` with the *canonical* spelling, asserting that the function returns `""` and that no INSERT statement is issued. This will guarantee coverage of the regression.

3. **Document the invariant** – in `store.py` comment that the dedup key must be unique for *any* spelling of a URL, not just for non‑canonical inputs, and reference the migration `idx_ke_chunk_dedup` as the enforcement point.

4. **Consider adding a database‑level trigger** (or a functional index) that normalises `source_url` on insert (e.g., a `GENERATED ALWAYS AS` column with the canonical form) and enforces uniqueness on that column, which would make the application‑level guard a safety net rather than the sole dedup mechanism. This would protect against any future bugs that skip the guard.

By fixing the guard to always check for an existing row, the system regains the guarantee that a logical document cannot be stored twice under different casings, preserving data integrity, preventing cross‑tenant leakage via duplicated IDs, and honouring the contract that “one canonical source URL = one row”. This addresses the hidden case‑sensitivity defect that the existing test suite missed.
