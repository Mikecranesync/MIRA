## 2. The hidden defect – `--paths` scope notice always empty

### 2.1 Where the bug lives

In **`tools/gate7_review.py`** (line ~820 in the current HEAD) the CLI builds the list of files that are *outside* the reviewer’s slice:

```python
paths = diff_paths(diff)                # <-- full list of changed files (a list of strings)
...
excluded = diff_paths_excluded(diff, tuple(paths))
```

`diff_paths_excluded` expects **prefixes** (the values supplied via `--paths`) so that it can return *all* changed files whose paths do **not** start with any of those prefixes.

The code mistakenly feeds it the full list of changed files (`paths`). Because every target path trivially starts with itself, the predicate `any(p.startswith(pre) for pre in prefixes)` is always true and **no file ever ends up in the `excluded` list**.

### 2.2 Why the test suite didn’t catch it

The unit tests that verify the SCOPE NOTICE (`test_scoped_run_tells_the_reviewer_which_files_it_cannot_see`) call `build_prompt(..., excluded=excluded)` directly, bypassing the CLI logic that computes `excluded`. Hence they exercise the rendering function correctly but never the path‑filtering code that populates the argument. The bug is therefore invisible to the existing test suite.

### 2.3 Impact on the platform

* **False‑positive findings** – A reviewer who runs `gate7_review … --paths docs/` will never see the “⚠️ SCOPE NOTICE”. The brief explicitly tells the reviewer “the only file changed is Y / the diff does not contain X is NOT a finding”. If the notice is missing, the reviewer may dutifully flag the *absence* of a code file as a defect, inflating the defect count and consuming rounds needlessly.

* **Silent‑scope failure** – More dangerous is the opposite direction: a malicious author can push a PR that changes a critical piece of production code **and** a documentation file. By invoking the reviewer with `--paths docs/` they hide the code change from the reviewer. Because the scope notice is empty, the reviewer never knows there is a hidden file, and the gate may PASS the PR even though a security‑relevant change slipped through unchecked.

* **Violation of Gate 7 doctrine** – The Gate 7 documentation (§ “SCOPE NOTICE”) mandates that every slice must be accompanied by an explicit list of excluded files, otherwise the review is considered **UNKNOWN**. The implementation now silently violates that contract.

### 2.4 Reproduction steps

1. Clone the repository and create a PR (or use the `gate7_review` CLI locally) that modifies at least one documentation file under `docs/` **and** a code file elsewhere (e.g. `mira-crawler/ingest/store.py`).  
2. Run the gate with the slice:  

   ```bash
   python -m tools.gate7_review 12345 --paths docs/
   ```

3. Observe the generated prompt: the “⚠️ SCOPE NOTICE” block is missing, even though the diff contains files outside `docs/`.  

4. If you add `--include-evidence` you’ll still see the same problem – the flag does not affect the bug.

### 2.5 Fix

Replace the erroneous argument with the user‑supplied prefix list:

```python
# Before (bug)
excluded = diff_paths_excluded(diff, tuple(paths))

# After (correct)
excluded = diff_paths_excluded(diff, tuple(a.paths))
```

*No other code changes are required* – the `excluded` list is then fed to `build_prompt`, which already renders the notice correctly (the tests for `build_prompt` will start passing the integration check).  

After the fix, re‑run the same scenario; the prompt now contains a properly formatted SCOPE NOTICE listing every file that the slice hides, and the Gate 7 contract is honoured.

|-------------|----------------|------------------|
| **`.log` files are now treated as documentation (`_DOC_SUFFIXES`)** | A PR that only updates a log file (e.g. a generated test‑run log) will be classified as “documentation”. That may be intended (logs are evidence artifacts) but could cause a pure‑code change that *also* updates a log to be classified as “mixed” and thus invoke a longer review flow. Verify that this behaviour matches the product intent and, if not, make the suffix list configurable per‑project. |
| **`canonical_source_url` does not normalise IDN hostnames** | Internationalised domain names are stored puny‑code in the DB. A URL with a Unicode host (`https://例子.测试/…`) will be lower‑cased but not puny‑code‑encoded, producing a different canonical string from the stored version, leading to missed deduplication. Consider applying `idna` encoding (`host.encode('idna').decode('ascii')`) after lower‑casing the host. |
| **`canonical_source_url` will lower‑case *any* “scheme:…“ string, even if it isn’t a URL** | The guard `if not sep or not _SCHEME_RE.fullmatch(head) …` prevents obvious false‑positives, but a string like `not:aurl` (a colon‑separated value that isn’t a URL) will be transformed to `not:aurl` (lower‑cased scheme). If such values ever make it to `insert_chunk` (unlikely, but possible via a malformed manifest) they will be stored with a lower‑cased scheme that does not reflect the original source. Add a stricter check that the scheme is one of the allowed network schemes (`http`, `https`, `file`, `ftp`, etc.) before canonicalisation. |
| **`parse_findings` now concatenates *all* `## FINDINGS` sections** | For legacy reports that contain multiple FINDINGS sections (e.g. a rendered list followed by a “Raw” section) the parser will merge them, potentially double‑counting the same finding if the author duplicated an entry. This is harmless for the current workflow (duplicate IDs are ignored) but could cause confusion in future tooling. Consider de‑duplicating by stable‑id after parsing, or explicitly only taking the **last** FINDINGS section (the one the reviewer actually authored). |
| **`parse_rulings` strict mode still accepts bare “F1 SUSTAINED” lines** | The new `_BARE_RULING_RE` is necessary for backwards compatibility, but it also matches a line inside a comment or a quoted snippet that is *not* a ruling, provided it lives inside the `## RULINGS` section. The strict adjudication shape validation already guarantees we only look inside that section, but a malicious author could embed a fake “F1 SUSTAINED” line inside a code block *within* the RULINGS section to subvert the verdict. Consider tightening the regex to require the line to be a list item (`-` or `*`) **or** wrapped in `**…**` as originally intended. |
| **`adjudication_verdict_strict` parses rulings twice** | The function calls `validate_adjudication_shape` (which parses the sections) and later calls `parse_rulings(text, strict=True)` again. This is a minor performance hit (negligible for current token limits) but doubles the regex work. Refactor to reuse the result of `parse_rulings` that `validate_adjudication_shape` already extracted. |

None of the above observations break the current test‑suite, but they represent either a subtle deviation from the documented contract (the `.log` classification) or a future‑proofing risk (IDN handling, ambiguous rulings). They are worth bringing to the attention of the owners before the PR is merged.

## 4. Conclusion

The PR introduces valuable fixes (case‑insensitive manifest discovery, canonical source‑URL handling) and solidifies the Gate 7 UI, but it **regresses the fundamental “SCOPE NOTICE” guarantee** by computing the list of hidden files from the wrong variable. This bug defeats the safety net that prevents reviewers from unintentionally ignoring code changes when using `--paths`, opening the door to silent‑scope attacks and wasted review rounds.

I recommend **rejecting the current head** until the `excluded` computation is corrected, the change is re‑run through the test matrix, and the additional observations above are either addressed or documented as intentional design decisions. Once the fix lands, the PR can be re‑submitted for a fresh Gate 7 review.
