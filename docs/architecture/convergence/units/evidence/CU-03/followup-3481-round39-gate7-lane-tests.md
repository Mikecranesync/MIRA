## FINDINGS
- **[severity: high] Scope prefix matching vulnerable to directory‑traversal via “..” sequences** — `filter_diff_paths` determines whether a file belongs to a scoped prefix by lower‑casing the raw diff path and checking `path.startswith(prefix)`. The function does **not** normalise the path (e.g. resolve “..”). An attacker can craft a diff entry that appears under a permitted prefix but actually resolves outside of it, thereby bypassing tenant‑scoping and evidence‑artifact exclusion.  
  **Evidence (verbatim diff line):**  
  ```diff
  diff --git a/docs/../src/secret.py b/docs/../src/secret.py
  ```  
  Because the raw prefix is “docs/”, the line is retained by `filter_diff_paths`, yet the real file is `src/secret.py`, a code file that should be out‑of‑scope. This can leak proprietary code or secrets to a documentation‑only review and violates the security boundary contract.

- **[severity: high] Renaming code files into documentation paths misclassifies review kind** — `pr_kind` classifies the review kind (code / documentation / mixed) solely from the **final** file paths after scoping and evidence‑artifact dropping. It does not consider the original file type. An adversary can rename a Python source file to a Markdown path, inject code changes, and the review will be briefed as “documentation‑only”, causing the lane to skip code‑review safeguards (evidence reminder, stricter redaction, tenant isolation).  
  **Evidence (verbatim diff snippet):**  
  ```diff
  diff --git a/src/secret.py b/docs/secret.md
  similarity index 100%
  rename from src/secret.py
  rename to docs/secret.md
  --- a/src/secret.py
  +++ b/docs/secret.md
  @@ -0,0 +1,5 @@
  +def hidden():
  +    # malicious logic
  +    pass
  ```  
  After the rename, `reviewed_paths` returns `docs/secret.md`; `pr_kind` therefore reports “documentation”. The high‑severity code change is hidden from the code‑review pipeline, breaking the architecture contract that code changes must trigger a code or mixed review.
