## Gate 7 – **Disprove the PR** – Findings & Recommendations  

**Scope of this review**  
The PR adds a full‑stack canonical‑URL handling layer, a “historical‑spelling” guard, stricter prompt‑shape validation for the Gate 7 reviewer and adjudicator, and a new evidence‑artifact exclusion pipeline. The changes are heavily exercised by the new test suite, but a subtle functional regression slips through the net: **duplicate logical entries can still be created when more than one historic (raw) spelling of the same logical URL exists**.

Below is a concise description of the defect, why it matters, how it can be reproduced, and a minimal fix that restores the original security guarantee.

---  

### 1. Summary of the defect  

| Component | Expected behaviour (as per design) | Actual behaviour (regression) |
|-----------|-----------------------------------|--------------------------------|
| `store.insert_chunk` (dedup guard) | Prevent any second row that represents the *same logical document* – regardless of which raw spelling was already stored – from being inserted. | The guard only checks for an existing row **with the exact raw spelling that the caller supplied** (`if raw_url != source_url and chunk_exists(..., raw_url, ...)`). If another historic row exists with a *different* raw spelling that canonicalises to the same logical URL, the guard does **not** fire, the `INSERT … ON CONFLICT DO NOTHING` does **not** conflict (the source URLs differ), and a *second* row is written. This re‑introduces the duplicate‑logical‑entry problem that Gate 7 round 6 was meant to eliminate. |

**Why this is a regression**  

* The PR’s own docstring (in `canonical_source_url`) states that “Historical residual, documented not migrated: rows written before this function keep their stored spelling… a one‑off dedup migration is the follow‑up, never a silent rewrite here.”  
* However, the *purpose* of the “historical‑spelling guard” in `insert_chunk` is to **prevent** a new canonical row from being written when **any** historic raw row for the same logical URL already exists. The current guard only prevents a duplicate when the *exact same* raw string is supplied again.  
* This opens the door to **duplicate logical entries** (two rows that represent the same document) whenever there are two different historic spellings – e.g. a case‑variant and a default‑port‑variant – for the same URL.  
* Duplicate rows break the uniqueness guarantee of the `idx_ke_chunk_dedup` index, corrupt ledger state, cause spurious “already‑ingested” reports, and can lead to contradictory visibility (`is_private`) settings. It is exactly the kind of *case‑sensitivity* defect that Gate 7 is meant to protect against (see round 6, round 12 findings).

---

### 3. Impact analysis  

| Impact | Description |
|--------|-------------|
| **Data corruption** | Two rows representing the same source document can be ingested, causing the dedup key `(tenant_id, source_url, chunk_index)` to hold two distinct `source_url`s for the same logical URL. Future ledger probes (`ingested_source_urls`) may return ambiguous results, and downstream KG‑linking may create duplicate entities. |
| **Visibility leakage** | If one of the duplicate rows is marked `is_private=True` and the other `is_private=False` (e.g., because the historic row predates a policy change), the “most‑private” rule is broken – a public row may be served even though a private version exists. |
| **Index violation** | The migration `003_kb_hardening.sql` creates a **UNIQUE** index on `(tenant_id, source_url, ((metadata->>'chunk_index')::int))`. Duplicate logical entries do **not** violate the index because the `source_url`s differ, but they defeat the *semantic* uniqueness guarantee the index is meant to enforce. |
| **Operational confusion** | The UI and audit logs will show two different source URLs for the same document, making it hard for operators to trace provenance, and may cause the “already‑ingested” check (`ingested_source_urls`) to miss one of the rows, leading to repeated re‑crawls. |
| **Security** | A malicious actor could deliberately submit two variants of the same URL (different case, different default‑port spelling) to force duplicate storage, inflating DB size or causing denial‑of‑service through unnecessary processing. |
