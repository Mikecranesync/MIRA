- **[severity: high] Duplicate logical entries due to asymmetric canonicalisation** — The new `canonical_source_url` function normalises scheme, host, default ports and percent‑escape case, and `insert_chunk` now **always** stores the canonical form. However, `chunk_exists` was updated to look up **both** the raw and canonical forms, but `insert_chunk` does **not** check for an existing raw row before inserting.  
  This means that if a historical row exists with the *raw* spelling (e.g. `"HTTPS://EXAMPLE.COM/Legacy.PDF"` stored before the canonicalisation fix), a fresh ingest of the same logical URL will insert a **second** row with the canonical spelling (e.g. `"https://example.com/Legacy.PDF"`). The unique index is on the exact `source_url` string, so the two rows coexist, violating the intended *exact‑match dedup* guarantee.  
  Consequences:
  * **Data duplication** – the same logical document appears twice, inflating storage and breaking downstream analytics that assume one row per document.
  * **Privacy regression** – a pre‑canonical row that was forced private (unclassified origin) can coexist with a canonical row that is classified as curated or public, effectively exposing content that should have remained private.
  * **State‑drift** – the ledger’s `ingested_source_urls` probe (which now queries both raw and canonical keys) will report the URL as ingested, but later processing that assumes a single row per URL may pick the wrong row, leading to inconsistent visibility enforcement.
  * **Idempotency break** – a re‑crawl of the same URL may insert a new row on each run after the fix, contrary to the contract that ingestion is idempotent after the first successful insert.

  *Root cause*: `insert_chunk` canonicalises the URL **before** calling `enforce_visibility` and **does not** guard against an existing raw‑spelled row. The original design relied on the fact that the stored key and the lookup key were identical; after introducing canonicalisation only the lookup was widened, not the write path.

  *Mitigation*:  
  1. Add a pre‑insert existence check that queries for both the raw and canonical forms (reuse `chunk_exists` logic) and abort the insert when either matches.  
  2. Alternatively, perform a **single‑source** canonicalisation step **before** any row ever exists (e.g. a migration that rewrites historical rows), then drop the raw‑lookup clause from `chunk_exists` to keep the invariant that the stored key is the unique canonical key.  
  3. Update the unique index comment/documentation to explicitly state that the canonical form is the authoritative key and that no raw rows may coexist.

- **[severity: medium] Mis‑classification of PR kind after evidence‑artifact exclusion** — `main()` computes `kind = pr_kind(scoped_paths(paths, tuple(a.paths)) if a.paths else paths)` **after** `drop_evidence_artifacts` has stripped all evidence files from the diff.   This silently hides the reminder that *preserved review artifacts are historical evidence, not present‑tense claims*, potentially leading reviewers to mis‑interpret quoted artifacts as current documentation.  
  *Impact*: Documentation‑only PRs lose the safety net that the brief explicitly provides, increasing the risk of false‑positive findings or missed policy violations.
