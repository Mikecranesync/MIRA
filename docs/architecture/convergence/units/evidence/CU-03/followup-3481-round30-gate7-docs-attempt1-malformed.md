## FINDINGS
- **[severity: high] Percent‑encoded host components are not normalised, enabling duplicate rows with divergent privacy settings** — `mira-crawler/ingest/store.py`  
  ```diff
  ++_PCT_ESCAPE_RE = re.compile(r"%[0-9A-Fa-f]{2}")
  ++def _upper_escapes(component: str) -> str:
  ++    """Upper‑case every valid %HH escape in *component*.
  ++    Nothing is ever decoded; invalid % text is left byte‑exact."""
  ++    return _PCT_ESCAPE_RE.sub(lambda m: m.group(0).upper(), component)
  ++
  ++def canonical_source_url(url: str) -> str:
  ++    """Lower‑case ONLY the scheme and the host of ``url``; every other byte —
  ++    userinfo, port, path, query, fragment — is preserved exactly as given.
  ++    The transform is idempotent."""
  ++    # ... scheme & host lower‑casing ...
  ++    # path, query and fragment are passed through `_upper_escapes` but never decoded
  ++    # e.g. "http://example.com/%61bc" becomes "http://example.com/%61bc" (lower‑case %61)
  ++    # the percent‑escape remains distinct from the decoded character "a"
  ++```
  The implementation deliberately **does not decode** percent‑escapes in the host (or any other
  component). Consequently, two URLs that resolve to the same host but differ only in the
  case of a percent‑escape (e.g. `http://example.com/%41` vs `http://example.com/%41` vs
  `http://example.com/%61`) are treated as distinct canonical keys. Because the uniqueness
  constraint (`idx_ke_chunk_dedup`) is applied to the **canonical key**, the database can store
  separate rows for these visually identical origins. If one row is inserted as private
  (`is_private = TRUE`) and another as public, the later ingestion of the same logical URL can
  expose private content to a tenant that only queried the public row, violating the intended
  isolation guarantee. This class of duplicate‑key privacy leakage is not covered by the
  existing test suite (which only asserts that escapes are upper‑cased) and therefore represents a
  high‑severity security defect.
