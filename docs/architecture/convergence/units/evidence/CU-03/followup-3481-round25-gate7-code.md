- **[severity: high] Inconsistent handling of surrounding whitespace in source URLs leads to duplicate rows and potential privacy breach** — `mira-crawler/ingest/store.py:73`  
  The `canonical_source_url` function does **not** strip leading or trailing whitespace before normalising the URL, while `_urls_in` in `origins.py` *does* (`n.value.strip()`). This mismatch can cause two logically identical URLs – one with whitespace and one without – to be stored as distinct rows, bypassing the deduplication guard and allowing private content to be ingested multiple times.  
  ```diff
  +def canonical_source_url(url: str) -> str:
  +    """The one storage identity of a source URL — the exact behaviour, nothing more:
  +    …
  +    """
  +    if not url:
  +        return url
  +    head, sep, rest = url.partition(":")
  +    …
  +    # No `strip()` on `url` – whitespace is preserved
  +    return url
  ```

- **[severity: high] Storing URLs with embedded user‑info (credentials) leaks secrets** — `mira-crawler/ingest/store.py:84`  
  `canonical_source_url` retains the `userinfo` component when rebuilding the URL (`{_upper_escapes(userinfo)}{at}{host.lower()}{port}{_upper_escapes(tail)}`), meaning any URL that contains `username:password@host` is persisted verbatim in `knowledge_entries`. This violates the secret‑handling policy and creates a high‑severity data‑leak vector.

  +        …

  +        host, colon, port = hostport.partition(":")

  +    …
  +    return f"{scheme}://{_upper_escapes(userinfo)}{at}{host.lower()}{port}{_upper_escapes(tail)}"

## NOT REVIEWED
- **Runtime behaviour under high concurrency** – The interaction between the pre‑insert `chunk_exists` guard and the `ON CONFLICT DO NOTHING` clause has not been exercised with a large number of parallel workers. It is possible that a race condition could allow two distinct raw spellings of the same logical URL to be inserted before either guard sees the other's row, leading to duplicate entries that bypass the intended deduplication.

- **Impact on existing data migrations** – The migration that introduced the `idx_ke_chunk_dedup` unique index (migration 003) was not re‑run after introducing the canonicalisation logic. It is unclear whether pre‑existing rows that violate the new canonical form will cause unexpected `ON CONFLICT` behaviour or index violations during a future bulk import.

- **Effect on downstream services** – The `knowledge_entries` table is consumed by downstream analytics pipelines that assume `source_url` values are raw, case‑preserving strings. Changing many URLs to a canonical form may break downstream joins or reporting unless those services are also updated. This area was not verified.
