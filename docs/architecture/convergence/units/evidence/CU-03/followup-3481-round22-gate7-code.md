## Findings

- **[high] insert_chunk returns a fabricated entry_id on conflict** — `ingest/store.py:insert_chunk` generates a UUID before executing the `INSERT … ON CONFLICT DO NOTHING` statement and returns it unconditionally. When the row already exists (either because a historical raw spelling is present or because the canonical key already exists), the `INSERT` does nothing but the function still returns a non‑empty string. Callers (e.g. `store_chunks`) treat any non‑empty return as a successful write and record the ID in the ingestion ledger. This creates a false‑positive indication that a knowledge entry was stored when it was not, breaking idempotency, corrupting the ledger, and enabling downstream pipelines to act on non‑existent data.
- **[high] race condition yields duplicate success reports** — In a multi‑worker environment, two ingest workers can simultaneously attempt to store the same logical document using different casings (e.g. `HTTPS://EXAMPLE.COM/file.pdf` vs `https://example.com/file.pdf`). Both see no historical raw row, both canonicalise to the same target, both call `insert_chunk`. One insert succeeds; the other hits the `ON CONFLICT DO NOTHING` clause but still returns a freshly generated UUID. Both workers report success to the ledger, leading to duplicate downstream processing (embedding, linking) and a divergence between the ledger and the actual DB state. This violates the contract that a duplicate should be silently ignored and not counted as a new entry.
- **[medium] unnecessary SELECT per insert adds latency** — The added historical‑spelling guard (`chunk_exists(tenant_id, raw_url, chunk_index)`) introduces an extra `SELECT COUNT(*)` before every `INSERT`. For high‑throughput ingestion (thousands of chunks per document) this extra round‑trip can become a measurable performance regression. While the guard is required for correctness, the current implementation does not leverage the DB’s `ON CONFLICT … RETURNING` facility to collapse the two operations into one.
