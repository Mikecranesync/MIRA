- **[severity: high] Origin discovery `_urls_in` still rejects uppercase scheme URLs** — the function `mira-crawler/ingest/origins.py:_urls_in` contains a case‑sensitive guard:

```python
if isinstance(n, ast.Constant)
and isinstance(n.value, str)
and n.value.startswith(("http://", "https://"))           # <-- case‑sensitive
and n.value.strip().lower().startswith(("http://", "https://"))
```

The first `startswith` check is evaluated *before* the lower‑casing check, so any constant written with an uppercase scheme (e.g. `"HTTPS://example.com/feed.xml"` or `"Http://mixed.example.com/x"`) is filtered out. This re‑introduces the defect that was originally reported in Gate 7 round‑12 (case‑insensitive origin discovery). As a result, manifests that contain uppercase‑scheme URLs are not discovered, the provenance policy consistency check is bypassed, and unclassified (potentially blocked) origins can be ingested unchecked. This is a security regression that could allow unauthorized or malicious content to enter the shared corpus.

**Impact:** Unclassified or blocked origins may be silently accepted, violating data‑ingestion policy and exposing the platform to credential leakage or malicious payloads.

**Suggested fix:** Remove the case‑sensitive `n.value.startswith(("http://", "https://"))` clause or replace it with a case‑insensitive check only:

```python
if isinstance(n, ast.Constant)
and isinstance(n.value, str)
and n.value.strip().lower().startswith(("http://", "https://"))
```

- **[severity: medium] `chunk_exists` query disables index usage** — in `mira-crawler/ingest/store.py:chunk_exists` the SQL uses an `OR` on `source_url`:

```sql
WHERE tenant_id = :tid
  AND (source_url = :url OR source_url = :raw)
  AND metadata->>'chunk_index' = :idx
```

The unique index on `(tenant_id, source_url, ((metadata->>'chunk_index')::int))` cannot be used because of the `OR`, forcing a sequential scan on `knowledge_entries`. An attacker could craft many look‑ups with distinct `:raw` values to drive high CPU and I/O, creating a denial‑of‑service vector.

**Impact:** Performance degradation and potential DoS under load, especially for large tables.

**Suggested fix:** Perform two separate queries (one for the canonical URL, one for the raw spelling) or use `IN (:url, :raw)` with a proper index hint, ensuring the index on `source_url` is leveraged.

- **[severity: low] Log fingerprint includes full URL hash, leaking credential entropy** — `_log_ref` in `mira-crawler/ingest/store.py` logs a SHA‑256 hash of the *entire* URL, which for a user‑info URL still contains the credentials before they are stripped from the visible part of the log:

```python
return f"{origin} sha256:{hashlib.sha256(url.encode('utf-8')).hexdigest()[:12]}"
```

While the credentials are not printed in clear text, the hash is a deterministic fingerprint of the full URL (including user‑info and query). If an attacker can observe many such hashes, they can perform offline dictionary attacks against low‑entropy credentials or tokens, effectively leaking secret material.

**Impact:** Potential credential disclosure through hash‑based correlation.

**Suggested fix:** Hash only the *public* part of the URL (scheme, host, and port) or replace the hash with a random opaque identifier generated at refusal time, ensuring no secret‑derived data is ever emitted.

- **[severity: low] `ingested_source_urls` now refuses empty or whitespace tenant IDs** — the function now returns an empty set and logs a warning when `tenant_id` is missing or whitespace‑only. Existing callers that relied on the previous cross‑tenant probe (e.g., audit tools that queried across tenants) will now receive no data, potentially breaking downstream processes.

**Impact:** Regression in tooling that expects a global “did this URL ever ingest?” check.

**Suggested fix:** Maintain backward compatibility by supporting an explicit `tenant_id=None` mode that omits the tenant predicate, or document the change clearly and update all callers accordingly.

- **[severity: low] `drop_evidence_artifacts` treats renames of evidence files as dropped even when the target path is non‑document** — the logic:

```python
moved_artifact = is_evidence_artifact(source) and target.lower().endswith(_DOC_SUFFIXES)
keep = not (is_evidence_artifact(target) or moved_artifact)
```

If an evidence artifact is renamed to a non‑document suffix (e.g., `.py`), `is_evidence_artifact(target)` is `False` but `moved_artifact` is also `False`, so the file is kept, which is correct. However, if the target ends with a document suffix but the content is now code (e.g., `.log` → `.py`), the artifact will still be dropped because `is_evidence_artifact(source)` is `True`. This could silently omit code changes from review if they are introduced via a rename from an evidence directory.

**Impact:** Potential for code changes to be excluded from the gate, reducing security coverage.

**Suggested fix:** Decouple the “artifact” classification from the file suffix check; only drop a file if *both* the source and the target are evidence artifacts (i.e., remain documentation/log), not merely based on the source’s prior location.
