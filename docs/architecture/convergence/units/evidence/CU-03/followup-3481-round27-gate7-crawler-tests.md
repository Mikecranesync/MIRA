## FINDINGS
- **[severity: high] Secrets in query strings are persisted to the database** — `store.canonical_source_url` deliberately preserves the query component of a URL (e.g., `?token=abc123`). The test suite only checks that the *log* does not contain the path or query:

  ```diff
  +        url = f"https://{blocked}/private/Secret-Doc-Name.pdf?token=abc123"
  ```

  ```diff
  +        assert "Secret-Doc-Name" not in text and "token=abc123" not in text
  ```

  However, there is **no test** asserting that the URL (including the query string) is *not* written to the `knowledge_entries.source_url` column by `store.insert_chunk`. Consequently, a URL that carries a secret token (or any credential) can be ingested and stored unchanged, leaking that secret to any actor with read access to the database, even if the origin is classified as `curated` (shared) or `private`. This violates the security requirement that credentials never be persisted and creates a privacy breach.

  Evidence of the missing safeguard is the absence of any assertion on the captured SQL parameters containing the full URL after an insert. The test `test_insert` and related fixtures only capture the `source_url` bound value but never verify that query parameters have been stripped or redacted. This structural blind‑spot means the implementation can unintentionally store sensitive query parameters.

  **Recommended remediation**: Strip or hash query parameters that match known secret patterns (e.g., `token=`, `api_key=`, `auth=`) before invoking `store.insert_chunk`, or reject such URLs outright at the ingest gate. Add a test that asserts the stored `source_url` does **not** contain a secret query component after insertion.

## NOT REVIEWED
- Behavior of `store.canonical_source_url` with Unicode whitespace (e.g., non‑ASCII space characters) surrounding URLs.
- Handling of explicit default ports during policy classification (e.g., `https://example.com:443/...` may bypass origin classification).
- Multi‑line `COPY` directives in Dockerfiles that could omit the provenance manifest.
- IDN (Internationalised Domain Name) handling in host normalization and policy look‑up.
- Performance impact of the `OR` clause in `chunk_exists` and `ingested_source_urls` queries on large datasets.
