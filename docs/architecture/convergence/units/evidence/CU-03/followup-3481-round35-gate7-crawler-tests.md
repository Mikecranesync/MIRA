## FINDINGS
- **[severity: high] `_whole_dir_copy_dest` is case‑sensitive and may miss Dockerfile COPY directives written in lower‑case**  
  The function matches only the literal token `COPY` using `re.match` without the `re.I` flag, e.g.:  
  ```python
  m = re.match(r"\s*COPY\s+(?:--\S+\s+)*(?:\./)?mira-crawler/?\s+([^\s#]+)\s*(?:#.*)?$", line)
  ...
  m = re.match(r'\s*COPY\s+(?:--\S+\s+)*\[\s*"(?:\./)?mira-crawler/?"\s*,\s*"([^"]+)"\s*\]\s*(?:#.*)?$', line)
  ```  
  Dockerfile instructions are case‑insensitive per the Docker spec. A Dockerfile that uses `copy` or `Copy` would bypass the whole‑directory‑copy detection, allowing a build that omits the provenance manifest. This defeats the F2 “manifest packaging” contract and opens a path for untracked ingest.

- **[severity: high] `_whole_dir_copy_dest` incorrectly accepts multi‑source COPY directives, yielding a false positive “whole‑directory” detection**  
  The same regexes above capture the first token after the `COPY` keyword as the source and the next token as the destination. With a Dockerfile line such as:  
  ```dockerfile
  COPY mira-crawler/ extra/ /app/
  ```  
  the pattern matches `mira-crawler/` as the source and mistakenly returns `extra/` as the destination, reporting success even though the manifest is not copied. This can let a malicious image be built without the provenance policy file, breaking the packaging contract (F2) and permitting ingestion of unvalidated content.

- **[severity: high] `_update_set_clauses` does not detect UPDATE statements that appear after a CTE (`WITH` clause)**  
  The scanner looks for `UPDATE` tokens directly, using the pattern:  
  ```python
  for m in re.finditer(
      rf"UPDATE{gap}+(?:\"?\w+\"?{gap}*\.{gap}*)?\"?knowledge_entries\"?(.*?)(?:\bWHERE\b|\Z)",
      text,
      re.I | re.S,
  )
  ```  
  This pattern cannot match an `UPDATE` that is preceded by a `WITH …` clause (e.g. `WITH cte AS (…) UPDATE knowledge_entries SET is_private = TRUE …`). An attacker could embed a visibility‑changing `UPDATE` inside a CTE, evading the scanner and allowing a private row to be unintentionally made public. The missed detection violates the F1 “Private‑visibility flag never updated on conflict” guarantee.

- **[severity: high] Credential‑query detection relies on a hard‑coded whitelist of parameter names, missing many common credential‑bearing names**  
  The test suite enumerates a specific list of query‑parameter names (e.g. `token`, `api_key`, `Authorization`) and asserts that only those trigger a refusal. The production code therefore likely uses the same static list (the test calls `provenance.url_credential_reason(url)`), meaning any credential passed via an unlisted parameter (e.g. `access-token`, `sessionid`, `auth_token`, `clientToken`) would be treated as benign and reach the store. This creates a security boundary breach where secret tokens can be stored in the database and potentially leaked.

- **[severity: high] `provenance.url_has_userinfo` does not detect percent‑encoded userinfo, allowing credential leakage via encoded authority**  
  The detection logic is exercised only on plain‑text userinfo strings (e.g. `https://user:pass@host`). It does not test or handle cases where the userinfo is percent‑encoded, such as `https://%75%73%65%72:%70%61%73%73@host/path`. Because URL parsing functions typically decode percent‑escapes only after separating the netloc, the current implementation may miss the encoded credentials, allowing them to pass the gate and be persisted. This violates the F3 “Undeclared runtime dependency on PyYAML” style security expectation that any credential in the URL must be refused before any SQL execution.
