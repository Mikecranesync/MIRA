### F1 — `simlab-gate` does NOT block merge, and three documents say it does

This is the finding that matters most, because "CI-gated" is the stated *basis* for simlab's
`CANONICAL` status.

The job's own comment (`.github/workflows/ci.yml:841-843`):

> The deterministic, no-LLM rubric grader **is a merge gate**: a diagnostic / UNS / citation
> regression on any of the six juice-bottling scenarios goes red here and **blocks merge**.

It does not. Two independent checks:

```
$ gh api repos/Mikecranesync/MIRA/branches/main/protection --jq '.required_status_checks.contexts'
["staging-gate","Hub E2E (command-center + onboarding)","mira-web pack tests","CI Gate","hold-gate"]
```

`SimLab Grader Gate` is not a required context — and it is not reachable transitively either,
because `ci-gate`'s `needs:` array lists eleven jobs and `simlab-gate` is not among them. A red
SimLab run therefore blocks nothing.

**The exclusion is deliberate and documented** — `ci.yml:1161-1164`:

> Intentionally NOT in the gate yet (stay visible; promote once reliable): secrets-scan (gitleaks
> license/rate flakes), docker-build-check (trivy drive-by CVE flakes + ~6 min), and the heavy
> quality gates **simlab-gate** / ocr-recall-gate / drive-pack-extract-tests / test-eval-offline.

So there is no bug in `ci.yml`'s *behaviour*. What exists is a **four-way documentation
contradiction** — declared vs observed, the CU-02 shape:

| Source | Says | True? |
|---|---|---|
| `ci.yml:1161-1164` | intentionally not gating, promote once reliable | ✅ the real, deliberate state |
| `ci.yml:841-843` (same file, 300 lines up) | "is a merge gate… blocks merge" | ❌ |
| `DUPLICATE_CAPABILITIES.md:34` | simlab is CANONICAL because "CI-gated (`simlab-gate` on every PR)" | ⚠️ it *runs* on every code PR; it does not *gate* |
| `docs/plans/2026-06-21-simlab-platform-oracle-implementation-plan.md:34` | "regressions block merge" | ❌ unmet intent |

**`CANONICAL` remains correct** — simlab is actively maintained (last commit 2026-06-24), has real
consumers (`tools/proof/`, two `tools/seeds/` files, `simlab/api.py`, `simlab/observe`), 34 modules,
and its own seed lane in `apply-seeds.yml`. But the *reason* the registry gives for it overstates,
and the promotion promised in `ci.yml` was never made.

### F2 — `mira-fault-detective` is NOT consumer-free: the canonical Supervisor names it

`mira-bots/shared/engine.py`:

```python
505  # diagnosis path pulls the latest diagnosis from mira-fault-detective's read-only
509  _LIVE_DATA_ENABLED   = os.getenv("MIRA_LIVE_DATA_ENABLED", "0") == "1"
510  _FAULT_DETECTIVE_URL = os.getenv("FAULT_DETECTIVE_URL", "http://mira-fault-detective:8077")
5259 """GET mira-fault-detective /current_fault. None on any non-ok response."""
5265 resp = await client.get("/current_fault")
5633 # legacy fault-detective block so the answer carries no duplicate or …
```

Gate 11 requires **zero API consumers**, not merely zero imports. This is an API consumer, in the
canonical engine, by name. Three qualifiers, all of which matter and none of which erase it:

- it is **flag-gated OFF** (`MIRA_LIVE_DATA_ENABLED` defaults to `"0"`);
- it is **superseded** — line 5633 dedups it against the FactoryLM overlay, which `wiki/hot.md`
  records as taking precedence when present;
- the test (`tests/test_live_data_enrichment.py`) **mocks** the HTTP call, so CI never touches a
  real service.

⇒ `mira-fault-detective` is **not deletion-safe** as things stand. Deleting it means first removing
`_build_live_data_context` and its config from `engine.py` — a change to the Supervisor, which is
a different risk class from deleting a bench directory.

This is CU-04's lesson repeating one unit later: **the blocker was not an import.** An
import-graph sweep clears this component; the Gate 11 API-consumer axis does not.

### F4 — simlab does NOT subsume them, and the gap is exactly the technician's daily work

`mira-fault-sim` models electrical and sensor-transient state that simlab's fault model does not:

```
mira-fault-sim/sim.py:67   debounced: bool
mira-fault-sim/sim.py:68   dropout_count: int
mira-fault-sim/sim.py:82   fuse_f2_ok: bool          (mode f2_blown darkens a whole sensor branch)
```

`mira-fault-detective` turns that into eight discrimination rules (`rules.py`):

`rule_estop` · `rule_f2_branch_loss` · `rule_jam` · `rule_vfd_no_motion` ·
`rule_dirty_or_misaligned` · `rule_pe101_local_wire` · `rule_vision_no_sensor` · `rule_pe101_chatter`

Several of those are the classic maintenance discriminations: **blown fuse vs broken local wire**
(`rule_f2_branch_loss` vs `rule_pe101_local_wire`), **flaky wiring vs genuine signal**
(`rule_pe101_chatter`, ≥5 dropouts/sec), and **sensor/vision disagreement in both directions**
(`rule_dirty_or_misaligned`, `rule_vision_no_sensor`).

simlab has none of that in its model:

```
$ grep -rln "fuse|dropout|debounce" simlab/
simlab/approval.py
simlab/docs/labeler01/electrical_io_notes.md
simlab/docs/filler01/electrical_io_notes.md
simlab/docs/filler01/spare_parts_notes.md
simlab/docs/capper01/electrical_io_notes.md
```

**Every hit is documentation, not simulation.** simlab's `docs/` describe electrical I/O because
those are the manuals MIRA is meant to cite — but `simlab/scenarios.py` (six scenarios, `_scenario_a`
through `_scenario_f`) and `simlab/baselines/` contain no fuse, no dropout counter and no
debounce state. simlab cannot generate a blown-fuse signature, so it cannot test whether MIRA
distinguishes one from a broken wire.

The two are **complementary, not redundant**:

| | `simlab` | `mira-fault-sim` + `mira-fault-detective` |
|---|---|---|
| Scope | 8 machines, whole line, cascading symptoms | one conveyor zone |
| Layer | process / PackML / UNS / citation quality | electrical + sensor transient |
| Transport | in-process, plus an MQTT **publisher** | MQTT **subscriber** — the read side |
| Graded by | deterministic no-LLM rubric | 8 hand-written rules |
| CI | runs on every code PR (does not gate — F1) | **none at all** |

The transport asymmetry is worth stating: `simlab/publishers.py` exercises the MQTT *write* path;
`mira-fault-detective/engine.py` is the only in-repo MQTT *subscriber*. Retiring it leaves the
read side of that contract with no reference consumer.

### F5 — both bench components are regression-blind

Both ship tests — `mira-fault-detective/tests/test_rules.py`, `mira-fault-sim/tests/` — and
**no CI job runs either**. This is the `ci.yml`-enumerates-test-paths trap (#3089, and the same
shape recorded in CU-03): a test file that is not named in a workflow runs nowhere, and a green
board says nothing about it.

That, not their existence, is the actual defect here. Whatever the owner decides, an unrun test
suite should not survive the decision.

## The decision — for the owner, not this unit

The backlog flags CU-08 as carrying a **"human taste decision on the bench harness"**. Three real
options, with what each costs:

### Option A — KEEP as a bench harness, and fix the honesty gaps *(recommended)*

Keep both, `EXPERIMENTAL`, bench-only. Then: enumerate their tests in CI so they stop being
regression-blind (F5), and fix the four-way `simlab-gate` contradiction (F1).

- **For:** they test electrical/sensor discrimination simlab structurally cannot (F4), which is
  core technician work; `mira-fault-detective` is the only MQTT subscriber in the repo;
  it is not deletion-safe anyway without an `engine.py` change (F2); the carrying cost is 8 source
  files behind an explicit bench-only banner.
- **Against:** two simulators invites "which one is canonical?" confusion — mitigated, not
  eliminated, by the banner.

### Option B — FOLD IN, then retire

Port fuse topology, dropout counters and sensor/vision asymmetry into `simlab/baselines/` +
`scenarios.py`, migrate the eight rules into the graded rubric, then retire both.

- **For:** genuinely one canonical simulator — the convergence doctrine's preferred end state.
- **Against:** real work on the CANONICAL component, and it must clear the `engine.py` coupling
  first. It also risks the classic strangulation failure: the port half-lands, and the estate is
  worse than either endpoint. Best sequenced as its own unit with its own R0, never as a
  by-product of a classification unit.

### Option C — RETIRE now

- **For:** smallest estate.
- **Against:** loses the electrical/sensor coverage outright (F4) and the only MQTT-subscriber
  reference (F4); requires an `engine.py` change first (F2); and orphans the demo assets — a
  12 KB runbook (`docs/conveyor-fault-detective-demo/README.md`) and six promo screenshots dated
  2026-05-27 → 05-31, which per the Screenshot Rule are an **append-only archive**.

**Recommendation: A now, B later if the estate is ever consolidated.** The deciding fact is F4 —
retiring today would delete test coverage for the fuse-vs-wire discrimination without anything
replacing it, and that discrimination is exactly what a maintenance agent exists to get right.
