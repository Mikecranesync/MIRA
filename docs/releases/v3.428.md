## Deploy checklist (prod)

1. **Migrations.** None were added since v3.427.0. Confirm **107_pilot_access.sql** is applied on prod before enabling approval: `SELECT 1 FROM schema_migrations WHERE version='107'` (or the repo's migration ledger query).
2. **Env (Doppler `factorylm/prd`).** These come from #4900, see `docker-compose.saas.yml`:
   - `PLG_POSTHOG_KEY`, `PLG_POSTHOG_HOST` for both web and hub. Empty means a no-op.
   - `PILOT_OWNER_EMAIL` sets who receives pilot-request emails.
   - `MIRA_PILOT_APPROVAL_REQUIRED`. Empty means **off**, i.e. open signup. It must be set to turn on the approval gate from #4882.
3. **Flags.** `PLG_CHECKOUT_ENABLED` must stay unset while pilots are free (#4369). Cohort and seat limits come from `PILOT_COHORT_MAX_ORGS`, `PILOT_SEAT_MAX_USERS` and `PILOT_WINDOW_DAYS` in `mira-hub/src/lib/config`.
4. **Smoke after deploy.** Register a disposable tenant and confirm it waits for approval. Request one pilot and confirm the owner email shows the lead source. Run one notebook question with a citation that opens. Confirm `/api/checkout` is refused.
5. **Release tag and deploy (GO from Mike).** `version-tag.yml` cuts a `v3.4xx.y` tag on every push to main. Prod deploys only through `deploy-vps.yml`, which is a manual dispatch pinned to an approved SHA:
   ```
   SHA=$(git rev-parse origin/main)       # the approved release candidate
   TAG=$(git tag --points-at "$SHA" | grep '^v3\.' | head -1)
   gh workflow run deploy-vps.yml -f approved_rc_sha="$SHA" -f approved_release_tag="$TAG"
   ```
6. **Rollback.** Redeploy the previous tag. A `rollback/<date>-v3.427.0` tag already exists (`git tag -l 'rollback/*'`).
