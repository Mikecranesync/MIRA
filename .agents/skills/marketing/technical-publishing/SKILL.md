# FactoryLM technical publishing

## Load the current phase

Work from the repository root. Read `docs/foundation/marketing/technical-publishing/README.md` and `PHASED-PLAN.md` in that directory. Inspect actual repository files before invoking a proposed command. Phase 1 documents the workflow; it does not ship a verified renderer or judge service. Complete one bounded phase and preserve its evidence before expanding scope.

Read `docs/foundation/marketing/style-guides/STYLE-GUIDE.md` for editorial rules. Use `docs/foundation/marketing/technical-publishing/examples/powerflex-525/` for the approved-reference identities, example input and source ledger. Use `JUDGE.md` for review and `MARKETING-EXPERIMENT.md` for distribution research. Reuse `BLOG-PLAN.md` for the existing Answer Radar integration; do not create another evaluator.

## Establish the evidence

Normalize the real reader question and identify equipment, version and important unknowns. Open the applicable primary sources, including adjacent warnings and continuation pages. Record publication identity, edition/date, URL, exact file hash and printed-to-PDF page mapping. Keep a claim ledger covering prose, tables, captions, metadata and calls to action.

Separate OEM statements, observations, editorial reasoning, hypotheses and verified outcomes. Preserve uncertainty. Scope or omit an unsupported assertion while continuing unrelated work. Do not infer a product defect from an article error or a successful repair from a cleared code.

## Author the document

Start with the reader's immediate question and next useful evidence. Put material prerequisites and consequences before instructions. Follow the guide's boundary for electrical/safety work. Use exact model/code/parameter labels and modest evidence-backed product wording. Omit prices and competitor promotion, including audit examples.

Use a direct lead, useful comparison/history tables, a clear handoff and exact source references. Preserve the approved navy/amber direction, readable native text, coherent spacing and restrained contact invitation. Do not impose an image count, FAQ quota or fixed page count.

Reuse the approved illustration when appropriate. For a new image, use the available authorized OpenAI image-generation capability, record its actual exposed model/tool identity and prompt, and inspect the result. Label generic/generated art. Use native text and deterministic diagrams/tables for technical information that must be exact. Never promise identical generation from a prompt alone.

## Build and inspect

Follow the current implemented tool instructions only after Phase 2 is complete. Until then, treat the proposed CLI and manifests as implementation requirements. Preserve approved references unchanged; place candidate exports separately. Record actual commands and limitations.

Inspect every final PDF page and the intended HTML sizes. Check native text, citations, annotations, table relationships, crop, contrast and footer clearance. Fix overflow by editing/reflowing or adding an intentional page; do not silently shrink essential text. Do not claim PDF accessibility certification from basic text/alt checks.

## Obtain independent judgments

Use separate technical and visual judge invocations, each independent of the author, with the complete evidence packet and `JUDGE.md`. Require actual source inspection and every-page visual comparison. Record identities and actual available model/tool versions; do not invent missing versions or fabricate reports.

Bind reviews to exact artifact, source, reference and render hashes. Treat missing evidence as UNKNOWN/BLOCKED, not PASS. Require correction of material technical/readability failures regardless of visual appeal. Apply at most two normal correction rounds; route a persistent material disagreement through the existing responsible reviewer. Rejudge affected output after edits.

A mechanical integrity gate verifies files and report consistency. It cannot establish truth, actual independence, equipment safety, product performance or publication authority by itself.

## Close the phase and preserve learning

Return the changed files/commit, work actually performed, evidence, unresolved findings and next bounded action. Update the phase ledger. Keep product evaluation and marketing results separate from editorial acceptance.

When product learning is in scope, retain the question/source/run/issue/retest relationship using Answer Radar's existing records. Classify the observation before proposing a repair. When marketing research is in scope, follow the experiment's task-based usefulness measures and attribution limits. Preserve existing authorizations; do not send messages, publish publicly or deploy without applicable authority.
